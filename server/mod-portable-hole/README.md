# Portable Hole commodity warehouse module

AzerothCore module + `PH1` addon protocol for a virtual commodity ledger. The default view is character-private; an account owner can explicitly grant another account a **read-only shared vault view**. The module supports authoritative GM credits (for seeding/operations), paged balance reads, reservations, release, and consume. Economic mutations remain character-scoped, backed by InnoDB transactions and durable request receipts. The server derives character and account identity from the session; client frames cannot select a mutation owner.

## Deliberate scope

- Stores fungible counts keyed by `character GUID + item_template entry`; only stackable, unlimited, non-quest item templates are accepted. Item IDs are checked through AzerothCore's `ObjectMgr`; no stock ID is guessed or included.
- Account sharing for the vault remains explicit and read-only: an authenticated account owner grants/revokes a viewer account ID; the viewer can aggregate that account's commodity balances. Pins, ordinary reservations, credits, receipts, and mutations remain scoped to the current character. A separate project ACL can authorize VIEW or CONTRIBUTE across accounts for a project budget; it does not grant general vault mutation rights.
- Migration `003_portable_hole_projects.sql` adds durable project targets, explicit account roles, and request-keyed reservations. Project contributors reserve eligible virtual balances from their own character; one atomic InnoDB update reserves both the contributor's character balance and the shared project target. Duplicate requests replay the stored result, project caps serialize competing contributions, and only the project owner or the contributing account may release a held contribution. Resource totals are planning/budget state, not craftable inventory.
- `REAGENTS <known-profession-spell-id>` is a read-only recipe advisor: the server validates the known profession spell, reads its native reagent list, and compares each reagent with the character's carried count and eligible virtual availability. It never makes virtual balance craftable or consumes it.
- This slice does **not** remove or materialize physical bag items, transport unique Item instances, price resources, or execute profession crafting. GM credit is a privileged server operation, not a player reward mechanism. Trusted modules can call `PortableHoleCreditFromServer` and `PortableHoleConsumeReservation`; a profession/reward adapter must still prove its own item/recipe transaction and cross-system recovery before minting balance or materializing a craft result.
- Reserved amounts remain part of total balance but cannot be reserved twice. `CONSUME` spends one complete active reservation; `RELEASE` returns its reserved amount to available balance. The unique receipt key makes duplicate requests replay the original result and rejects reuse with different parameters.

## Install/test prerequisites

1. Load `sql/characters/001_portable_hole_warehouse.sql`, `002_portable_hole_vault_access.sql`, then `003_portable_hole_projects.sql` into a disposable Characters DB in filename order. These additive migrations create the module's InnoDB ledger, receipts, pins, explicit read-only vault access, and separately scoped project ACL/reservation tables; they do not drop or seed core data.
2. Install the module directory under AzerothCore `modules/`, copy `conf/mod-portable-hole.conf.dist` to the matching runtime config location, and load the `PortableHole` addon from `addon/PortableHole`.
3. The test-only credit operation is accepted only for a GM and only for the GM's own character. Browse valid stackable `item_template` entries from the server's checked-out content; do not put guesses in the config or SQL.

## Protocol

Client frames are bounded ASCII/tab records on `LANG_ADDON` channel `PH1`. Supported opcodes are `HELLO`, `LIST`, `BAG`, `NEED`, `REAGENTS`, `SEARCH`, `SHARE`, `PINS`, `PIN`, `PLAN`, `CREDIT` (GM-only), `RESERVE`, `RELEASE`, and `CONSUME`. `SHARE <viewer-account-id> GRANT|REVOKE` is executed as the current authenticated owner account; the server ignores client-supplied owner identity. `LIST` and `SEARCH` accept an optional account ID for an aggregate vault view and fail closed unless it is the viewer's own account or an active grant exists. These views expose balances only—reservation and mutation operations still use the current character. The addon displays the account ID returned by the server so players can exchange IDs for an explicit grant. `REAGENTS <spell-id>` accepts only a recipe spell the character knows and the pinned core classifies as a profession spell; it reports native recipe reagent counts, carried counts, bag gaps, and eligible virtual availability. Virtual availability is advisory and cannot satisfy the craft. `BAG <item-entry>` is read-only and reports AzerothCore's carried inventory count for an eligible stackable item; bank counts are excluded. `NEED <item-entry> <required-count>` compares that carried count with the requested quantity and separately reports available virtual balance. The virtual count is explicitly **not craftable from this view** and is not added to carried stock. The addon keeps a local character-keyed convenience copy of up to ten pins and can synchronize them to server-side Characters DB storage; the server is authoritative and enforces the cap and character scope. Owned ledger rows can be searched by item name and sorted by entry, name, total, or available count. The `PLAN` view calculates a candidate bulk deposit from carried inventory but explicitly does not transfer or reserve items. Request IDs are required for economic mutations and are bounded safe tokens. `guid` never appears in a request. The server throttles requests, limits page and operation sizes, filters unavailable item templates from output, and returns the receipt read back from the durable table after commit. On database uncertainty, the client gets `RETRY` and must repeat the same request ID.

Project commands use the addon slash command and remain server-authorized: `/ph project create <key> <item-entry> <target>`, `/ph project grant <key> <account-id> [VIEW|CONTRIBUTE]`, `/ph project revoke <key> <account-id>`, `/ph project show <owner-account-id> <key>`, `/ph project reserve <owner-account-id> <key> <amount>`, and `/ph project release <owner-account-id> <key> <reservation-request-id>`. Project keys and amounts are bounded, IDs are derived from the authenticated session except for the explicitly selected owner/key lookup, and every requested project operation checks the account's owner/ACL role. Only `CONTRIBUTE` can reserve; `VIEW` is read-only. The owner and contributor can release a held reservation. There is intentionally no project consume/craft opcode: consumption would require a separately qualified, atomic inventory/craft bridge.

## Qualification

The repository's disposable MySQL suite tests the same table/transaction/receipt contract for collision, idempotency, competing requests, process death, replay, and rollback. The public-core compile workflow compiles this module against pinned AzerothCore. Neither check is a booted-server/client gameplay qualification. See `docs/22-expanded-gameplay-program.md` for the shared-contract boundaries.
